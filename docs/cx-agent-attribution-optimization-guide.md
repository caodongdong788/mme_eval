# cx-agent 归因优化分类与使用指南

本文用于统一 MME 对 cx-agent 的问题归因、任务汇总和优化建议展示。适合产品、算法、医学、研发和其他 AI 直接引用。

## 1. 目标

归因不是重新打分，而是回答四个问题：

1. 哪个扣分点确实由 cx-agent 引起；
2. 执行链上最早失败的节点在哪里；
3. 应修改哪个真实组件；
4. 应采取哪类可执行优化动作。

分类遵循以下原则：

- 原因、组件和修改动作分开记录，避免把“RAG 优化”“流程优化”当成万能分类；
- 只归责最早失败节点，下游表现只作为影响，不重复归责；
- 单 Case、任务汇总和 Open API 使用同一份结构化分类；
- 不从中文建议关键词推测类别；
- 不能定位的新增原因显示为“归因分类待补充”，不会静默落入“其他”。

本次设计基于 cx-agent `sit` 分支代码快照 `ecf9ae69`，覆盖主 Agent、Prompt/Hook、上下文工具、医学文献 RAG、工具执行、终答协议、模型运行时及 undercurrent 主动服务等链路。

## 2. 归因输出结构

每个原子扣分项包含以下稳定字段：

```yaml
optimization_classification:
  domain: medical_rag
  component: rag_grounding
  failure_mode: rag_not_grounded
  action_type: grounding_rule
  evidence_status: sufficient
  coverage_status: mapped
```

字段含义：

| 字段 | 含义 |
|---|---|
| `domain` | 一级优化领域，共 8 个 cx-agent 领域 |
| `component` | 需要修改或排查的真实组件 |
| `failure_mode` | 最早失败节点的问题代码 |
| `action_type` | 应实施的修改类型 |
| `evidence_status` | 证据是否充分：`sufficient`、`partial`、`insufficient` |
| `coverage_status` | 分类覆盖状态：直接命中 `mapped`、按责任模块兜底 `owner_fallback`、尚未纳入 `unmapped` |

建议同时带责任范围：

```yaml
recommendations:
  - scope: cx_agent
    priority: P1
    target: RAG 证据利用
    action: 回答生成前逐条核对最终选中文献与关键结论
```

`scope` 只能是：

- `cx_agent`：确认属于 cx-agent 的优化；
- `evaluation`：Benchmark 或判分模型需要复核；
- `evidence`：证据不足，需要先补链路数据。

## 3. 八个 cx-agent 优化领域

| 一级领域 | 组件范围 | 典型问题 |
|---|---|---|
| 医学安全与策略 | 医学安全策略 | 风险分级、禁忌、就医时效、危险建议拦截错误 |
| Prompt、Hook 与专家配置 | 静态 Prompt、动态 Hook/Reminder、专家包 | 规则缺失、规则冲突、动态提醒未注入、专家配置错误 |
| 用户上下文与长期记忆 | 用户档案、病历、Timeline、历史对话、病例夹、咨询对象、记忆写入 | 该读未读、读到未用、对象错误、新旧冲突、记忆写入失败 |
| 对话与工具编排 | 意图路由、追问、能力开关、工具注册/选择/参数/策略/执行、主动服务 | 路由错误、缺少追问、工具不可见、参数错误、被阻断、执行失败或超时 |
| 医学文献 RAG | 触发、服务调用、Query、知识库、召回、阈值、候选、重排、证据利用、引用绑定 | 未触发、调用失败、检索词错误、召回不足、重排错误、证据未用、引用错配 |
| 临床推理与方案合成 | 事实提取、时间线、风险收益、禁忌/相互作用、临床合成 | 事实读错、时序错误、忽略禁忌、风险收益失衡、方案拼接错误 |
| 回答生成与交付协议 | 内容组织、完整性、沟通风格、终答协议、A2UI、SSE/前端交付 | 漏答、表达不当、只输出 function call、消息分段错误、图片/卡片未兑现 |
| 模型运行时与可观测性 | 模型调用、流式超时、部分输出、上下文窗口、压缩、工具结果预算、证据采集 | API 失败、超时、空输出、上下文截断、compaction 丢信息、链路证据缺失 |

Benchmark 判据、判分模型和标注/RAG 冲突单独属于 `evaluation_system`，不计入 cx-agent 八个领域，也不会通过 Open API 输出为 cx-agent 缺陷。

## 4. 关键判定规则

### 4.1 上下文与长期记忆

必须区分：

- `context_not_fetched`：用户信息没有进入当前上下文；
- `context_not_used`：信息已经进入上下文，但回答没有使用；
- `context_subject_error`：本人、家属或其他咨询对象归属错误；
- `context_stale_or_conflict`：新旧资料冲突，错误使用过期信息；
- `memory_write_error`：长期记忆写入、更新或去重失败。

不能因为回答“不够个性化”就直接归为 Prompt 问题。应先检查用户档案、病历、Timeline、历史对话和病例夹是否到达模型上下文。

### 4.2 工具与对话编排

必须区分：

- 工具没有注册或未进入 active tools；
- 工具存在但模型没有选择；
- 工具参数不合法；
- 工具被策略或权限拦截；
- 工具执行失败；
- 工具执行超时；
- 工具结果被上下文预算截断。

这些问题不能统一写成“对话流程问题”。追问不足归 `clarification`，意图或流程分支错误归 `intent_routing`，能力开关错误归 `feature_gate`。

### 4.3 医学文献 RAG

按执行顺序寻找最早失败节点：

1. 是否需要 RAG；
2. 是否触发；
3. 调用是否成功；
4. Query 是否完整；
5. 原始召回是否包含相关信息；
6. 是否通过阈值；
7. 是否进入候选；
8. 是否被最终选中；
9. 回答是否正确使用；
10. 引用是否与来源一致。

精确判定：

| 证据表现 | 归因 |
|---|---|
| 应检索但未调用 | `rag_not_called` |
| 已发起调用但接口失败 | `rag_call_failed` |
| 原始召回没有相关内容，不能证明知识库缺文档 | `rag_recall_error` |
| 能证明知识库缺失或过期 | `rag_corpus_gap` |
| 原始召回有、阈值后无 | `rag_threshold_error` |
| 阈值后有、最终未选，但没有候选成员证据 | `rag_candidate_or_rerank_error` |
| 候选中有、最终未选 | `rag_rerank_error` |
| 最终选中但回答未使用 | `rag_not_grounded` |
| 最终选中但理解或外推错误 | `rag_misinterpreted` |
| 回答标注的引用与文献/chunk 不一致 | `citation_mismatch` |
| 应展示来源但缺少可回链引用 | `missing_rag_reference` |

“RAG 未触发”和“RAG 调用失败”不得合并；候选阶段证据不足时不得直接归责重排器。

### 4.4 临床推理与回答表达

如果输入事实本身已正确到达模型，但模型在事实提取、时序、禁忌、风险收益或方案合成上出错，归入临床推理。只有医学事实和结论正确、问题发生在组织、完整性、语气或格式时，才归回答生成与交付。

### 4.5 输出协议与运行时

- `<msg_break />`、function call 与终答关系、A2UI、图片/文献资源绑定、SSE 和前端卡片属于交付协议；
- 模型 API、流式超时、部分输出、上下文窗口、compaction 和工具结果截断属于运行时；
- Langfuse 或快照缺少必要节点时归可观测证据不足，不能提前归责业务组件。

## 5. 优先级

- `P0`：可能造成医学安全风险，或高置信度的关键系统错误；
- `P1`：影响多个 Case、关键能力或核心正确性的系统问题；
- `P2`：局部完整性、表达和低影响优化。

优先级只描述处理顺序，不决定责任领域。同一领域可以同时存在 P0、P1、P2。

## 6. 单 Case 与任务汇总

单 Case 和任务汇总均按以下稳定键聚合：

```text
责任范围 + 评测问题类型 + failure_mode + 原因标签
+ domain + component + action_type + 根因阶段
```

因此：

- 相同组件、相同失败模式但业务原因不同的项不会错误合并；
- 单 Case 与任务总结展示相同的“领域 · 组件”；
- 任务总结不会凭建议中文内容重新猜分类；
- 评测系统问题不会混入 cx-agent 优化建议；
- 未识别的新原因会显示为“归因分类待补充”，便于及时扩展分类表。

## 7. 新增 cx-agent 能力时的接入要求

新增模块、工具或执行阶段时，需要同步完成：

1. 新增明确的 `failure_mode`，不要复用含义不同的旧代码；
2. 将失败模式绑定到现有 8 个领域中的真实组件；
3. 定义 `action_type`；
4. 在 Langfuse/快照中保存能够证明输入、决策、输出和错误的证据；
5. 增加归因分类测试；
6. 如果确实不属于现有组件，扩展组件表，但不要新增“其他优化”。

系统会自动校验归因 Prompt 中出现的所有原因代码均已存在分类映射。未来出现未知原因时，`coverage_status=unmapped`，证据状态自动降为 `insufficient`，防止遗漏被误当成已确认缺陷。

## 8. 已修复的历史问题

- 原分类混合“根因、模块、修改动作”，同类问题在汇总和明细中展示不一致；
- RAG 分类过细但 Prompt、上下文、工具、临床推理、协议和运行时覆盖不足；
- `rag_call_failed` 被合并成 `rag_not_called`；
- 无候选成员证据时错误归责重排；
- 缺少引用错配分类；
- 用户信息未读取与读取未使用混为一类；
- 建议责任范围依赖中文关键词正则猜测；
- 不同业务根因可能被聚合到同一个模糊问题；
- 新增原因可能静默落入“其他”。

以上问题已通过结构化分类、统一归一化、稳定聚合键、建议 `scope` 和覆盖状态检查修复。
